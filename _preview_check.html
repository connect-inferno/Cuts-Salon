How Cuts-Salon talks to Firebase

One private Firebase project per salon, found through a small optional directory. This page is the end-to-end reference: what's built, what's deliberately not built yet, and the exact steps to bring on the next salon.

01

How many Firebase projects will there be?

One per salon, plus at most one small shared project that isn't a salon at all — it just answers “which salon does this email belong to.”

Formula

Total projects = (number of salons) + 1 optional directory project

Today: 1 salon (cuts-salon) + 0 directory = 1 project live
Once the directory is set up: 1 salon + 1 directory = 2
At 5 salons: 5 salons + 1 directory = 6 total

The directory never holds salon data and can be skipped entirely — sign-in still works without it, just by trying each salon project in turn. It only exists to keep that trying-each-one step fast as the salon count grows.

02

Why separate projects, not one shared one

A single shared Firebase project would technically hold every salon's data — that's literally what the old Postgres backend did before this migration. The reason it isn't done that way now is isolation, not capacity: with separate projects, a bug in one salon's access rules can only ever expose that one salon's customers and bills. In a shared project, the same class of bug exposes every salon at once, through the same code.

Firestore quotas and Firebase Auth are also scoped per project, so one salon's traffic spike or bug can never eat into another's usage.

03

The full picture

Five salons, drawn as a concrete example. The app either asks the directory once (dashed, optional) or falls back to trying each salon's own Firebase Auth directly (solid). Either route lands on exactly one salon project — the directory is a shortcut through the same set of boxes, not a different destination.

04

How signing in actually works

Two paths reach the same two outcomes. That's deliberate: from the outside, a wrong password and an unknown email look identical, and a directory hit that fails looks identical to a fallback loop that fails — nothing about the response reveals which salons an email might belong to.

06

Why cost stays flat as a salon grows

Firestore bills per document read, not per user. The app used to re-read a salon's entire bill history — every bill ever created — on almost every action: creating a bill, clocking in, clocking out. That cost grows every month a salon stays open, forever. It's fixed now.

CollectionBeforeNow
Billsevery bill ever created, every reloadmost recent 300
Attendancefull historymost recent 500
Commissionsfull historymost recent 1,000
Discount requestsfull historymost recent 300
A customer's total spent / visit countsummed from every bill, every timeone number, stored on the customer, updated atomically per bill

At the scale discussed — roughly 1,000–3,000 client visits a month — this keeps a salon comfortably inside Firestore's free daily allowance rather than climbing into real monthly cost by its first year.

07

Bringing on a new salon

Five steps, done once per salon. The fifth is the only one tied to the directory, so it's the only one that's optional today.

  1. 1
    Create the Firebase projectConsole or firebase projects:create. Enable Firestore + Email/Password Auth.
  2. 2
    Deploy rules and indexesfirebase deploy --only firestore:rules,firestore:indexes --project <salonId>, using firestore.rules / firestore.indexes.json.
  3. 3
    Create the ownerAn Auth account, an employees/{uid} document with role OWNER, and a settings document.
  4. 4
    Register the salon in the appAdd a SalonFirebaseConfig entry to salon_directory.dart with the new project's web config.
  5. 5
    Register in the login directory — optionalAdd emailDirectory/{email} → {'{'} salonId {'}'} for the owner. Skipping it just means this salon's logins always use the fallback loop.

09

Decisions, and why

Separate projects, or one shared project?

Separate. One shared project is technically enough and was how the old backend worked, but one rules bug there exposes every salon at once instead of one.

Does the login directory store passwords?

No, and it never should. It holds only email → salonId. Real password checks stay at each salon's own Firebase Auth, exactly as before — a compromised directory can misdirect a lookup but can never itself leak a password.

Can the directory be written from the app?

No — writes are fully locked in firebase-directory.rules. An openly-writable directory would let anyone repoint someone's email at an attacker's own project and capture their real password on the next login attempt.

Is the directory required?

No. It only exists to keep sign-in fast as the salon count grows. Skipping it costs nothing but speed at scale — the fallback loop is the entire mechanism today, with 1 salon configured.
